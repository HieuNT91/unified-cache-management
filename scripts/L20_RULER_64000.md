# L20: RULER, exactly 64000 input tokens, thinking enabled

Use the existing Python environment and local Qwen3-32B checkpoint. Get code with
Git and source assets from NVIDIA RULER and its official dataset providers.
No environment installation or archive transfer between servers is needed.

The experiment has **800 prompts × 19 configurations = 15,200 measured generations**:

- 100 samples each: `cwe`, `fwe`, `vt`, `qa_1`, `qa_2`, `niah_multivalue`,
  `niah_multikey_2`, `niah_multikey_3`.
- No-cache baseline; ProphetKV at **1,5,10,15,20,30,40,60,80%**; selective ProphetKV
  at those same nine ratios, using **zero-based layers 11,12,13,14,15**.
- **Exactly 64,000 formatted input tokens**, including chat template, chunk
  markers, padding and the fresh question suffix. This is not 65,536.
- Native thinking enabled; **16,384 generated tokens maximum**, shared by
  thinking, answer and control tokens. Temperature0.6, top_p0.95, top_k20, seed0.
- BF16, YaRN4 (32768 → 131072), TP4, KV chunks4096, **16384 scheduled prefill
  tokens per step**. Prefix caching disabled; baseline has no connector.

Two TP4 groups use physical **GPUs0–3** and **GPUs4–7**, pinned to the UUIDs below.
Each processes 50 samples/task, all 19 methods: **7600 measurements per group**.
GPUs8–9 stay free. This uses the existing TP4 implementation with memory headroom;
there is no ten-way tensor-parallel configuration in this runner.

## Download official assets and prepare on CPU

```bash
# Network access, CPU only. Clones NVIDIA/RULER and downloads its source assets:
bash scripts/l20_ruler.sh download

# Generate 100 examples/task and freeze exact token IDs. CPU only, no KV building:
bash scripts/l20_ruler.sh prepare

# Verify both shard configurations without loading GPU libraries or model weights:
bash scripts/l20_ruler.sh dry-run
```

RULER is a generator, so downloading its assets alone does not produce the final
64000-token inputs. The download command pins NVIDIA/RULER to
`c3f5e3b4f87f97e048793bb510a3a6b19a46bf3a`, materializes and verifies the official
Git LFS CWE word list, downloads SQuAD2 dev and HotpotQA dev-distractor, runs NVIDIA's
Paul Graham essay downloader, and downloads NLTK sentence-tokenizer data. HotpotQA
tries the official CMU endpoint first, then the exact mirror supplied by NVIDIA's
download script. Existing valid assets are reused; download provenance/hashes are
recorded in `RULER_SOURCE/asset-downloads.json`. Essay download logs list any URLs
that NVIDIA's downloader skipped; the resulting corpus hash is frozen.

Sources:
[NVIDIA RULER](https://github.com/NVIDIA/RULER),
[NVIDIA download script](https://github.com/NVIDIA/RULER/blob/c3f5e3b4f87f97e048793bb510a3a6b19a46bf3a/scripts/data/synthetic/json/download_qa_dataset.sh),
[SQuAD](https://rajpurkar.github.io/SQuAD-explorer/),
[HotpotQA](https://hotpotqa.github.io/).

Preparation uses the pinned task definitions and seed42. It generates with a
63360-token source budget and 128-token generator reserve to leave room for chat
and chunk formatting. This generator reserve does not set inference output length:
inference always has the requested **16384** cap. The native thinking chat template
is applied without appending RULER's forced assistant answer prefix.

The full original prompt and question tokens are preserved. Newline tokens are
inserted before the user text, inside the user message, until the final formatted
input is exactly64000. The fresh suffix is rounded up to a multiple of64 and
contains the complete final question, with a minimum of256 tokens. Padding counts
and source identities are recorded per sample; oversized inputs fail rather than
being truncated. This exact-length thinking protocol is an adaptation of RULER,
not its standard leaderboard protocol. Every method uses identical frozen tokens.

`PREPARED_DIR/preparation.json` records counts, hashes and padding ranges.
Completed matching preparation is reused; changes to sources, tokenizer or
preparation code require a new PREPARED_DIR. Interrupted generation resumes from
verified task receipts. Raw rows stay under `PREPARED_DIR/raw/`.

## Run detached

```bash
mkdir -p "$EXPERIMENT_DIR" "$CACHE_ROOT"
nohup setsid bash scripts/l20_ruler.sh run \
  > "$EXPERIMENT_DIR/launcher.log" 2>&1 < /dev/null &
echo "Coordinator PID: $!"
```

Each group runs its baseline prompts in a connector-free engine, then loads one
cached engine for all remaining measurements. For each prompt it **builds KV once,
waits for every TP shard, runs all18 cached configurations, validates results and
transfer retirement, then deletes that prompt's KV**. No collection-wide KV setup
is needed. Selection and repaired KV stay private to each request.

Retained BF16 KV is at most **15.5625GiB per group**, **31.125GiB total**. The disk
check reserves twice that plus16GiB scratch: **78.25GiB**, with additional space
needed for prepared inputs, diagnostics and results. It runs before GPU creation.

A coordinator lock and per-group output directories reject duplicate launches.
Ordinary failures shut down the owned engine before deleting its private temporary
cache. A hard kill or failed shutdown can leave the current prompt's cache; its
unique path is recorded in `group-N/plan.json`. Keep validated outputs and inspect
failures before arranging a recovery. No automatic resume or historical job control
is installed, and these instructions do not authorize running jobs on another server.

## Live and final aggregation

Per-method `live_aggregation.{json,csv,md}` updates automatically after each
validated and retired measurement. Both groups contribute under a shared report
lock. To combine all19 methods into one live report:

```bash
bash scripts/l20_ruler.sh status
cat "$EXPERIMENT_DIR/live_summary.md"
tail -n 40 "$EXPERIMENT_DIR/launcher.log"
tail -n 40 "$EXPERIMENT_DIR/group-a.log" "$EXPERIMENT_DIR/group-b.log"
```

The launcher automatically writes `final_summary.{json,csv,md}` after all15200
measurements, both engines' shutdown receipts and cache deletion. To regenerate
the final combined tables without GPU work:

```bash
bash scripts/l20_ruler.sh aggregate
cat "$EXPERIMENT_DIR/final_summary.md"
```

Each method has **overall and per-task** accuracy, mean/median TTFT, thinking/answer
content-token lengths, control-token counts, output-cap counts and unfinished
thinking counts. Overall means are prompt-weighted; all eight tasks have100 samples.
TTFT ends at the first generated token, including thinking. Construction, warmup,
priming, validation and retirement are separate from TTFT. Per-prompt outputs,
token IDs, exact selection diagnostics, construction costs and deletion receipts
remain available in the result directory.

Accuracy uses NVIDIA's case-insensitive substring rules on the **answer channel**:
mean reference coverage for CWE/FWE/VT/NIAH and any-reference match for QA1/QA2.
Missing answers from unfinished thinking score0. These are RULER scores, not QA
exact-match/F1 scores or scores on the reasoning text.

CPU validation covers exact length/source preservation, all19 configurations,
balanced task shards and synthetic15200-record final aggregation. Real CPU
preparation is checked on one sample of each task with the Qwen3 tokenizer.
GPU execution/equivalence on these L20 devices remains unverified; no local GPU
jobs were launched for this command preparation.

If startup reports `invalid literal for int()` with a `GPU-...` UUID, update to
the repository's UUID compatibility fix. Stock vLLM 0.9.2 assumes integer device
IDs in its NVML metadata queries. UCM now resolves UUIDs before attention backend
imports, including in spawned workers, without changing `CUDA_VISIBLE_DEVICES`.
No site-packages edits or GPU ordinal substitutions are needed.

After the failed launcher has exited, pull the fix and choose a new results
directory; the launcher refuses to overwrite partial results. Prepared inputs
can be reused. For the server whose checkout is directly under `/data/jh`:
